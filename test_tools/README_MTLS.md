# mTLS Testing for Flicker

This directory contains functional tests for mTLS (mutual TLS) authentication in Flicker.

## Overview

The mTLS tests verify that Flicker can:
- Load client certificates and private keys
- Establish secure HTTPS connections with client authentication
- Send log batches over encrypted mTLS connections
- Verify server certificates using a custom CA

## Quick Start

Run the automated end-to-end test:

```bash
./test_tools/test-mtls-e2e.sh
```

This script will:
1. Generate test certificates (if needed)
2. Start an HTTPS server that requires client certificates
3. Start Flicker with mTLS configuration
4. Generate test logs and verify they're sent over mTLS

## Manual Testing

### Step 1: Generate Test Certificates

```bash
./test_tools/generate-test-certs.sh
```

This creates:
- `test_tools/certs/ca.crt` - CA certificate
- `test_tools/certs/ca.key` - CA private key
- `test_tools/certs/server.crt` - Server certificate
- `test_tools/certs/server.key` - Server private key
- `test_tools/certs/client.crt` - Client certificate for Flicker
- `test_tools/certs/client.key` - Client private key for Flicker

### Step 2: Start the mTLS Receiver

In terminal 1:
```bash
./test_tools/test-mtls-receiver.py
```

This starts an HTTPS server on port 8443 that requires client certificates.

### Step 3: Start Flicker with mTLS

In terminal 2:
```bash
./target/release/flicker -c test_tools/test-mtls-config.yaml
```

### Step 4: Generate Test Logs

In terminal 3:
```bash
./test_tools/test-log-generator.py --path test_tools/test-mtls.log --volume high
```

You should see in terminal 1 (receiver) that batches are being received with client certificate authentication.

## Configuration

Example mTLS configuration:

```yaml
log_files:
  - path: "/var/log/app.log"
    polling_frequency_ms: 250
    buffer_size: 100
    flush_interval_ms: 30000
    destination:
      type: "http"
      endpoint: "https://secure-server.example.com/ingest"
      tls:
        cert_path: "/etc/flicker/certs/client.crt"
        key_path: "/etc/flicker/certs/client.key"
        ca_cert_path: "/etc/flicker/certs/ca.crt"  # Optional
        accept_invalid_certs: false  # Not recommended for production
```

## Certificate Requirements

- **cert_path**: Client certificate in PEM format
- **key_path**: Client private key in PEM format (PKCS#8 or traditional RSA)
- **ca_cert_path**: (Optional) Custom CA certificate to verify the server
- **accept_invalid_certs**: (Optional) Set to `true` to accept self-signed server certificates (for testing only)

## Verifying mTLS is Working

When Flicker starts with mTLS configuration, you should see:
```
[HTTP] Configured mTLS with client certificate from /path/to/client.crt
```

When sending batches, you should see successful sends without SSL errors:
```
[HTTP] Sending batch of 50 entries to https://...
[HTTP] Batch sent successfully (HTTP 200)
```

If there's a certificate problem, you'll see errors like:
- `Failed to create identity from certificate and key`
- `Failed to read certificate file`
- `SSL handshake failed`

## Troubleshooting

### Certificate Format Errors

If you get "Failed to create identity", ensure your certificates are in PEM format:

```bash
# Check certificate format
openssl x509 -in client.crt -text -noout

# Check key format
openssl rsa -in client.key -check
```

### Connection Refused

If Flicker can't connect, verify:
1. The server is running and listening on the correct port
2. The endpoint URL in the config matches the server
3. Firewall rules allow the connection

### Server Certificate Verification Failed

If the server uses a self-signed certificate:
1. Add the server's CA certificate to `ca_cert_path`
2. Or set `accept_invalid_certs: true` (testing only!)

### Client Certificate Not Accepted

Ensure:
1. The client certificate is signed by a CA the server trusts
2. The certificate hasn't expired
3. The private key matches the certificate

## Security Notes

⚠️ **WARNING**: The certificates generated by `generate-test-certs.sh` are for TESTING ONLY!

For production use:
- Obtain certificates from a trusted Certificate Authority
- Use proper key management (hardware security modules, key vaults, etc.)
- Never commit private keys to version control
- Rotate certificates regularly
- Use strong key sizes (4096-bit RSA or 256-bit ECC minimum)
- Keep private keys encrypted at rest
